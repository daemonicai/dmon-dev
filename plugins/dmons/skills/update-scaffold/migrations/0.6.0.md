# Migration → 0.6.0 — sections, not blocks; the procedure moves to the plugin

**Applies to:** any repo scaffolded with **0.5.1** (stamped `<!-- dmons-scaffold: 0.5.1 -->`). A repo
coming from 0.5.0 applies `0.5.1.md` first; from 0.4.x, `0.5.0.md` before that; and so on.

**Also applies to a `0.6.0-<preview>` target** — see SKILL.md Step 2. It does **not** carry a repo from
one 0.6.0 preview to another; re-scaffold for that.

Two changes land together, and they touch the same files, so they migrate together.

## What changes

**1. `block` is retired; every agent moves up one level.** The unit of work is the `## N.` section
(or group — whatever the repo's `{{UNIT}}` term is). Nothing is merged and nothing is deleted:

| Agent | 0.5.1 | 0.6.0 | Model |
|---|---|---|---|
| `worker` | implements a block | implements a **section** | sonnet (unchanged) |
| `reviewer` | audits a block | audits a **section** | sonnet → **opus** |
| `supervisor` | audits a section | audits the **whole change**, once | opus (unchanged) |

One commit per section instead of per block. The reviewer's loop is bounded at two remediation passes.
The supervisor's `Request changes` no longer triggers a remediation block automatically: every section
is already committed by then, so the Architect **stops and notifies the Product Owner** instead.

**2. The procedure leaves `CLAUDE.md`.** The ~150 lines of loop (select, pre-flight, implement, the
supervisor section, done) move into the new **`/dmons:implementation`** skill, which wraps
`opsx:apply`. `CLAUDE.md` keeps the project's facts, roles, boundaries, and a short instruction to
invoke the skill at every section boundary, and gains a machine-readable **`# dmons-config`** block the
skill reads its values from. The tripwire gains a `boundary` mode that reminds the Architect to
re-invoke the skill after each of its commits.

**Say this to the user before starting — it is the one irreversible part of 0.6.** After this
migration the repo holds the configuration and the agents, and the procedure arrives from the plugin.
A teammate who clones the repo without the `dmons` plugin can read the configuration but cannot run the
implementation phase, and two people on different plugin versions can run different procedures on the
same change. `/dmons:implementation` checks the stamp against its own version on every invocation to
catch that second case.

## Migrations, in order

Harvest first (SKILL.md Step 3). Everything M1 writes into the new config block comes out of the
existing `CLAUDE.md`, and it has to be read **before** M1 deletes the sections it lives in:

- `{{UNIT}}` — the term used in `## 3.`'s headings;
- the gate commands from **Commands** and the §3b gate list, including format/lint where present and
  the per-stack gate sets and `make gates-all` on a multi-stack repo;
- the worker roster — the Roles bullets, cross-checked against `.claude/agents/worker*.md`;
- `{{HITL_EXAMPLES}}` — the human-in-the-loop bullet in §4;
- `{{DECISIONS_NOUN}}` — from the §3b brief step;
- the co-author line — from the §3b commit block.

### M1 — `CLAUDE.md`: configuration stays, procedure goes *(in-place, several edits)*

Work top to bottom. Heading levels are relative (SKILL.md Step 5).

**a. The DEVLOG conventions** (above the `---`). Replace the "Organised by" and "Each post is
attributed" bullets and the base-commit bullet with:

> - Organised by `## N.` **{{UNIT}}** (mirroring `tasks.md`), then a `## Change review` heading for the
>   supervisor's end-of-change audit, with a pinned `## NEXT` at the bottom.
> - Each post is **attributed** — prefixed with the author's role: `[architect]`, the worker's name
>   (`[worker]`, or `[worker-<stack>]` for a per-stack worker), `[reviewer]`, `[supervisor]`.
> - **The first post under each `## N.` heading is the {{UNIT}}'s base commit** —
>   `**[architect]** Base: <sha> — <what this {{UNIT}} delivers>`. It is the reviewer's scope for the
>   {{UNIT}}, and the first one is the supervisor's scope for the whole change — not ceremony.

In the append-only bullet, "committed with each block" becomes "committed with each {{UNIT}}", and drop
"The whole review loop lives here." from the questions bullet.

**b. Commands.** "When a block adds a project" → "When a {{UNIT}} adds a project".

**c. Boundaries.** "an agent under pressure to finish a block" → "…to finish a {{UNIT}}". Append to the
tripwire bullet:

> The same script also reminds you, after each of your commits, to re-invoke `/dmons:implementation`
> (see *The implementation phase*).

In **When the tripwire fires**, "the block skipped a gate" → "the {{UNIT}} skipped a gate" and "run the
block through the rest of the loop" → "run the {{UNIT}} through…".

**d. The authority clause — rewrite, don't move.** Replace the paragraph beginning **"This section is
authoritative."** with:

> **Authority is split by kind.** This document is authoritative for **project facts, roles, and
> boundaries** — who owns what, which commands gate the work, what the agents may not do.
> **`/dmons:implementation`** is authoritative for **the implementation procedure** — the order of
> steps, the handoffs, the gate/tick/commit cadence. Any `opsx:*` skill is subordinate to both: if one's
> behaviour conflicts with either, follow this document or `/dmons:implementation`, whichever covers
> the point.

This is the edit most likely to do harm if done wrong. Left as it was, the old sentence tells the
Architect to prefer the (now deleted) in-file loop over the skill — or, if any of it survives a partial
migration, to prefer the stale copy exactly when the two disagree. If the user skips the rest of M1,
**do not apply this edit either**, and do not skip this edit while applying the rest.

**e. The three-phase map.** Replace the intro line and the three bullets with the template's
(`scaffold/templates/CLAUDE.md.template`, from "A change moves through three phases:"). The third
bullet is now **Implementation** (`opsx:apply`, via `/dmons:implementation`).

**f. Roles.** Keep the section; it is needed in every phase. Within it:

- Architect hat: "during `opsx:propose` and the whole apply below — … read specs, carve work into
  blocks, brief agents…" → "during `opsx:propose` and the implementation phase — … read specs, brief
  agents…".
- Worker bullet(s): "implements each block" / "implements … blocks" → "implements each {{UNIT}}" /
  "implements … work".
- Replace the `reviewer` and `supervisor` bullets with:
  > - **`reviewer`** agent — audits each {{UNIT}}'s diff (one reviewer for the whole change, every stack).
  > - **`supervisor`** agent — audits the whole change once every {{UNIT}} has landed (one supervisor,
  >   every stack).
- **Delete** the paragraph **"The two auditors have different jobs and must not be swapped."** — it is
  loop mechanics, and the agents' own files say it.
- In **"You are the only agent that invokes agents."**, delete the sentence "the reviewer runs when
  **you** spawn it, the supervisor runs when **you** spawn it at {{UNIT}} end" and change "the
  workflow's loops would run without you" → "the loop would run without you".

**g. Delete the procedure** — `## 1. Select the change`, `## 2. Pre-flight`, `## 3. Implement` with all
of `3a`/`3b`/`3c` (and the per-stack block-routing line inside §3, if present), and `## 5. Done`. In
their place, after Roles, insert the template's **`## The implementation phase — invoke
`/dmons:implementation` at every {{UNIT}} boundary`** section verbatim, with `{{UNIT}}` filled.

**Hand edits in the deleted sections are the risky part.** A repo that tuned its procedure — an extra
gate step, a project-specific commit rule, a note about a flaky test — loses that tuning when the
sections go, because the skill cannot carry it. Before deleting, diff each section against what the
0.5.1 template would have produced and show the user every divergence. For each, they choose: keep it
as a short project-specific note (under Roles or Commands — a fact about this repo, not a step of the
loop), or drop it. Never silently discard one, and never keep one by re-growing a procedure section.

**h. Stop and ask.** Rename to **Stop and ask — the Product Owner's calls**. Keep the four general
triggers (ambiguity/contradiction, out of scope, Open Question, spec is wrong). **Remove** the
human-in-the-loop bullet, the supervisor-still-requests-changes bullet, and the **On stopping
mid-block** paragraph — all three move to the skill. Change the lead-in to "Stop, **notify**, and ask"
and append the template's paragraph beginning "The Product Owner may not be watching the transcript."

**i. Add the configuration block** — the template's **`## Workflow configuration`** section, at the end
of the OpenSpec Workflow region, filled from the harvest. It must parse: keep the `# dmons-config` first
line, every key, two-space indentation, and quote the `coauthor` value. Delete any optional line
(`format`, `lint`, `every_stack`) the repo has no target for. Check it with a quick YAML parse if one is
to hand, and read it back to the user.

### M2 — worker(s): implement a section *(in-place, each `worker*.md`)*

Against `scaffold/templates/worker.md.template`, replace these passages and leave every slot value as
the repo has it:

- the per-stack line, if present: "every block routed to you" → "every brief routed to you";
- "You are invoked by the **Analyst/Architect** … running the OpenSpec Workflow in `CLAUDE.md`." → the
  template's sentence naming `/dmons:implementation`;
- **`## Your job: implement one block`** — the whole section, heading and both paragraphs and the two
  bullets, with the template's **`## Your job: implement one {{UNIT}}`** (three paragraphs — the
  section, the split range, remediation passes — and the same two bullets re-scoped);
- the `CLAUDE.md` bullet in **Authoritative context** → "project facts, roles, and boundaries";
- in **The DEVLOG**, the lead-in and first and last bullets, as in the template (post as you go; hand
  off when the whole brief passes);
- **How you implement** steps 1 and 4, as in the template (plan the section; self-test as you go);
- **Boundaries**: "commits per block" → "commits once per {{UNIT}}"; "at {{UNIT}} end" → "at the end of
  the change"; "If a block seems to need" → "If the work seems to need"; "your block needs a target" →
  "your {{UNIT}} needs a target"; "from within a block" → "from within a {{UNIT}}";
- **Stop and report**: "the block needs a `Makefile` target" → "the {{UNIT}} needs…";
- **Communication**: "When you finish a block" → "When you finish a brief".

Then `grep -n -i block` the file: every remaining hit should be the verb (*blocked*, *blocks the tool
calls*) or the frontmatter's `hooks:` block.

### M3 — reviewer: audit a section, on opus *(in-place)*

- **Model.** If the frontmatter says `model: sonnet`, propose `model: opus` and say why: it is now the
  only audit a section gets, on a diff several times larger, with the supervisor no longer backstopping
  it per section. **If it says anything else, the repo chose that deliberately — do not move it.** Flag
  it and let the user decide.
- Replace the opening two paragraphs after the title line and the **Stay diff-local** paragraph with
  the template's (through **Stay {{UNIT}}-local**), and insert the template's **`## Your scope — the
  {{UNIT}}'s diff`** section after it. The `git status --short` line matters: the section is reviewed
  uncommitted, and new files don't appear in `git diff`.
- **Authoritative context**: the `CLAUDE.md` bullet → "project facts, roles, and boundaries", and the
  spec bullet gains "(read the requirements this {{UNIT}} claims to deliver, not just its tasks)".
- **The DEVLOG**: "under the block's {{UNIT}}" → "under the {{UNIT}}'s heading"; replace the Request
  changes bullet with the template's (two remediation passes, then the Product Owner).
- **Correctness**: "the block's tasks" → "the {{UNIT}}'s tasks"; "A block whose gates were run" →
  "Work whose gates were run".
- **OpenSpec scope**: replace with the template's three bullets, and insert the template's
  **`### Coherence within the {{UNIT}}`** after it — the within-section drift check the old supervisor
  used to cover, which is now the reviewer's by construction.
- **How you report** and **Do not approve when**: as in the template ("this {{UNIT}}", the new
  "a task the worker reports complete has no counterpart in the diff" bullet).

**Harvest check — `{{DOMAIN_HAZARDS}}`.** These were authored diff-local, and the reviewer is still
diff-local — just on a bigger diff — so they usually transfer as they are. Read them once anyway for any
bullet that says "block" or assumes a small diff, and show the user a rewording rather than editing it
silently.

### M4 — supervisor: audit the whole change *(in-place, most of the file)*

Nearly every prose paragraph in `supervisor.md` changes level — "block" becomes "section", "section"
becomes "change". **This note sanctions replacing the template-structure prose section by section from
`scaffold/templates/supervisor.md.template`**, which is otherwise a wholesale rewrite the guardrails
forbid. It is sanctioned on one condition: **every slot value is carried across** —
`{{SUPERVISOR_TITLE}}`, `{{PROJECT_*}}`, `{{COMPLIANCE_NOUN}}`, `{{LANG}}`, `{{ADR_CONTEXT_LINES}}`,
`{{BINDING_DECISIONS}}`, `{{DECISIONS_*}}`, `{{GRAPHIFY_TOOL_LINE}}`, the gate targets — and any hand
edit outside the slots is shown to the user before it is replaced.

Two harvested values need re-reading at the new altitude rather than copying:

- **`{{SUPERVISOR_DESCRIPTION}}`** (frontmatter). It says the supervisor runs after a section's last
  block lands. Re-compose it: change-level auditor + project + what it catches that a section review
  can't + runs once, after every section of the change has landed. Show the user old and new.
- **`{{ARCHITECTURAL_COHERENCE_BULLETS}}`**. Authored as "structural risks that accumulate across
  blocks", now read against a whole change. Most transfer — a public-API-consistency bullet is true at
  either level — but a bullet phrased around blocks, or one that only makes sense inside a single
  section (and so now belongs to the reviewer), needs attention. Propose rewordings bullet by bullet;
  never edit them silently. The slot transferring cleanly is not the same as its text reading right.

The new file's DEVLOG section files posts under `## Change review`, not under a `## N.` heading.

### M5 — hook scripts *(in-place, full rewrite, both)*

Overwrite `.claude/hooks/dmons-guard.sh` and `.claude/hooks/dmons-tripwire.sh` from their templates,
stripped of `#!!` lines and otherwise verbatim, stamp line 2, then `chmod +x` both and confirm with
`test -x`.

- **Guard:** the enforcement logic is byte-identical to 0.5.1. Only the deny messages changed — they
  told a blocked worker the Architect "commits once per block", which now describes a loop that no
  longer exists. Say so: nothing about what is blocked has changed.
- **Tripwire:** `start`/`stop`/`report` are unchanged apart from the same wording. The new `boundary`
  mode is inert until M6 wires it.

### M6 — wire the boundary reminder in `.claude/settings.json` *(in-place, additive — ask separately)*

Merge into the existing `hooks` object, appending to `PostToolUse` if the repo already has entries
there:

```json
{ "hooks": {
    "PostToolUse": [ { "matcher": "Bash", "hooks": [ { "type": "command",
        "command": "\"$CLAUDE_PROJECT_DIR/.claude/hooks/dmons-tripwire.sh\" boundary" } ] } ]
} }
```

It runs after every Bash call in the Architect's session and in subagents; the script exits silently
unless the call was the Architect's own (no `agent_id`) `git commit`, the commit actually landed, and a
change is in flight. What it injects is one line: re-invoke `/dmons:implementation` before the next
section.

**Ask separately**, as for every `hooks` change. Declining is legitimate but has a cost worth stating:
without it, the only thing that brings the procedure back into context at a section boundary is the
three-line instruction in `CLAUDE.md`, and a long run or a compaction is exactly when that gets missed.

### M7 — verify end to end *(user action, not an edit)*

1. **The guard still holds.** Ask a worker to commit something. It should come back
   `BLOCKED by the OpenSpec Apply Workflow`. If it commits, the frontmatter hooks are being skipped —
   workspace trust or a lost execute bit.
2. **The reminder fires.** In the main session, make a throwaway commit while a change is active (then
   `git reset --soft HEAD~1`). The next turn should carry the `dmons: that commit is a section
   boundary` reminder. If it doesn't, check M6's wiring and that `jq` is on `PATH`.
3. **The skill finds its configuration.** Run `/dmons:implementation`. It should orient from the
   `# dmons-config` block without asking what the gate targets are, and without a version-skew warning.

## In-flight changes

A change mid-apply has a DEVLOG written in block conventions and some sections supervised per section.
Post the SKILL.md Step 7 note, and in it:

- **Leave the DEVLOG as written.** Per-block posts and per-section supervisor reviews are the true record
  of how those sections were built.
- **A section half-built under blocks** — some blocks committed, the section not yet closed — finishes
  under the new procedure: brief the remaining tasks as the worker's range, and have the reviewer audit
  the whole section from its `Base:` (the already-committed blocks included — that is the within-section
  coherence pass the per-section supervisor would otherwise have given it). Commit the remainder as the
  section's closing commit.
- **No section gets a retroactive supervisor review.** The change review at the end covers every
  section, including those built and supervised under 0.5.1.
- If an earlier section never got a `Base:` post, the change base for the supervisor is the change
  branch's merge-base with the default branch; say so in the note.

## Verify after applying

- `grep -n 'dmons-config' CLAUDE.md` finds exactly one block, and it parses as YAML with every key
  present and no `{{` left in it.
- `CLAUDE.md` contains **no** `3a.`/`3b.`/`3c.`, no "block by block", and no "This section is
  authoritative" — and does contain the split authority clause and the instruction to invoke
  `/dmons:implementation`.
- `grep -n -i 'block' .claude/agents/*.md` returns only the verb and the `hooks:` block.
- `reviewer.md` is on `opus` — or on whatever model the user chose to keep, recorded in the report.
- `test -x` both hook scripts; no `#!!` line survives in either.
- `jq -e . .claude/settings.json` parses; `grep -c 'dmons-tripwire' .claude/settings.json` is exactly 4
  if M6 was applied (3 if not); `permissions.allow` still holds every rule it had.
- Every file the scaffold owns carries `<!-- dmons-scaffold: 0.6.0 -->` (or the preview version being
  tested); the `Makefile` carries `# dmons-scaffold: …` on line 1 and each hook script on line 2. The
  `Makefile` itself needs no edit for 0.6.0 — re-stamp it only.
- **M7 has actually been run**, not just read.
