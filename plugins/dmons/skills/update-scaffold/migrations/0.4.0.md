# Migration → 0.4.0 — the Makefile is the command surface

**Applies to:** any repo scaffolded with **0.3.x** (stamped `<!-- dmons-scaffold: 0.3.0 -->` or
`0.3.1`). A repo coming from 0.2.x applies `0.3.0.md` and `0.3.1.md` first, then this note.

## What changed in 0.4.0

The workflow shape is untouched — same two nested loops, same roster, same models. What changed is
**how a gate is run and how its result is established**.

Before 0.4.0 the scaffold wrote each project's raw toolchain commands into `CLAUDE.md` and every agent:
`dotnet build`, `npm --prefix web test`, `openspec validate <change> --strict`. Two problems compounded.
The commands drifted — the same gate was spelled differently in four files, and moving a toolchain meant
finding every copy. And an agent decided whether a gate passed by **reading the tool's output**, which
is unreliable in a specific, load-bearing way: `dotnet format --verify-no-changes` exits 2 while
printing a single `warning: IDEnnnn` line, output that scans exactly like a clean run with a note beside
it. That has been reported as a passing gate.

0.4.0 puts a root **`Makefile`** in front of both. Every gate is a target, every target ends by printing
its own exit code as `LABEL_EXIT:<n>` and exiting with it, and the agents are told to **quote the code,
never interpret the log**. Raw commands live in exactly one file; everything else names targets.

```
build:
	@dotnet build; code=$?; echo "BUILD_EXIT:$code"; exit $code
```

Target set: `build` / `test` / `format` (a **check**, never a rewrite) / `lint` (only where genuinely
distinct from the formatter), the OpenSpec-common `validate` and `changes`, `-k` gate sets (`gates`,
plus `gates-<stack>` and `gates-all` when multi-stack), and the non-gate `publish` / `clean`. The
primary stack owns the unprefixed targets; every additional stack is prefixed (`web-build`,
`gates-web`), matching its worker name.

**M1 gates the whole note.** If the Product Owner declines the Makefile, M2–M7 must be skipped as well —
applying them alone leaves every agent calling targets that don't exist.

## Harvest before applying

From the existing files (see SKILL.md Step 3):

- the `{{UNIT}}` term in use;
- **the raw commands**, from `CLAUDE.md`'s "Commands" section and the agents' build/test/format lines.
  These become the Makefile's recipes verbatim — do not re-derive them from the repo, and do not
  "improve" them. If `CLAUDE.md` and an agent disagree about a command, surface it to the user rather
  than picking one;
- the **worker roster and stack names** — they fix the target prefixes and gate-set names;
- **any existing `Makefile`**: its recipes are the project's own and outrank anything you'd infer.

**Audit fresh only for what the 0.3.x files can't contain**, and confirm each with the Product Owner
rather than guessing:

- a **`lint`** command, where the stack has a linter distinct from its formatter (eslint, clippy,
  `ruff check`). .NET has none — analyzers run inside `dotnet build`;
- **`publish`** and **`clean`**, if the project genuinely has them. A service deployed by CI often has
  no publish command; omit the target rather than inventing one;
- the optional one-sentence **exit-code rationale** naming a tool in *this* project that exits non-zero
  while printing innocuous output. Omit it if there's no real example.

## Migrations, in order

M1 first — everything else names the targets it defines.

### M1 — generate `./Makefile` *(new file, or a confirmed merge)*

Fill `${CLAUDE_PLUGIN_ROOT}/skills/scaffold/templates/Makefile.template` from the harvest: the raw
commands as recipes, one section per stack, the spec section verbatim, the gate sets composed from the
stack targets. Strip every `#!!` line; **keep** the plain `#` comments. Recipe lines are **tab**-indented.

**Show the Product Owner the complete file and ask apply / edit / skip** — this is not a batchable
additive migration, even though it creates a new file. It encodes inferred commands, and a wrong recipe
fails silently by never running a gate.

**If the repo already has a `Makefile`:** merge, never replace. Keep every existing recipe as-is and
propose only the additions — the `LABEL_EXIT:` echo on recipes that lack it, `validate`, `changes`, the
gate sets, `.PHONY` entries. Present the echo on an existing recipe as its own accept/decline; a project
that wants its recipes untouched can take the targets without them, in which case say so in M2/M3 and
leave the exit-line assertions out of the agents for those gates.

**Declined → stop here.** Report that the repo stays on raw commands, skip M2–M7, and stamp nothing.

### M2 — `CLAUDE.md`: the Commands section *(in-place, replaces a section)*

Replace the `### Commands` section — the one bullet list of raw commands — with:

> ### Commands — the Makefile is the command surface
>
> Every gate runs through the root **`Makefile`**. Build, test, format, lint, and spec validation are
> `make` targets; **do not call the underlying toolchain directly**. That keeps the command names stable
> as the toolchain moves underneath them, and — the load-bearing part — **every gate target prints its
> own exit code** as `LABEL_EXIT:<n>` on its last line.
>
> **Read the exit line, not the output.** A gate passed only if you saw `BUILD_EXIT:0`. Tools routinely
> exit non-zero while printing output that scans exactly like a clean run, and a gate has been reported
> as passing on that basis before. Quote the code; don't interpret the log.
>
> - Build: `make build` → `BUILD_EXIT:0`.
> - Test: `make test` → `TEST_EXIT:0`, all green.
> - Format: `make format` → `FORMAT_EXIT:0`.
> - Validate the active change(s): `make validate` → `VALIDATE_EXIT:0`.
> - Whole gate set in one pass: `make gates` → `GATES_EXIT:0`. It runs the set with `-k`, so one
>   invocation reports **every** failing gate instead of hiding the rest behind the first.
> - List active changes: `make changes` (or the directories under `openspec/changes/`, excluding
>   `archive/`).
>
> `make publish` and `make clean` are **not** gates and no agent runs them — they are the Product
> Owner's.
>
> **The Makefile is yours (Architect), not the workers'.** When a block adds a project, a test suite, or
> a stack that the existing targets don't cover, *you* update the Makefile and say so in the DEVLOG. A
> worker that needs a target changed stops and reports it; it does not edit the Makefile, and it does not
> route around it by calling the raw toolchain.

Drop the format and lint bullets the project has no target for; add a `lint` bullet where M1 emitted one,
and one gate-set line per additional stack (`make gates-web` → `GATES_WEB_EXIT:0`) plus `make gates-all`.
Keep any project-specific command bullets the repo had added — move them down, don't delete them.

### M3 — `CLAUDE.md`: the §3b gate list *(in-place, replaces a list)*

In §3b step 5 (**Gates — all must pass before ticking any box**), replace the raw-command bullets with:

> 5. **Gates — all must pass before ticking any box.** Run each and **read its exit line**; a gate
>    passed only when you saw its `LABEL_EXIT:0`:
>    - `make build` → `BUILD_EXIT:0` (no errors)
>    - `make test` → `TEST_EXIT:0` — the block's new tests **and** all existing tests
>    - `make format` → `FORMAT_EXIT:0`
>    - `make validate` → `VALIDATE_EXIT:0`
>
>    `make gates` runs the whole set in one `-k` pass and is the quickest way to get the full picture —
>    but a green `GATES_EXIT:0` is what you're after, and a red one still needs the individual exit
>    lines to say which gate failed. Never conclude a gate passed from reading its output; quote the
>    code.

Note the heading levels are relative (SKILL.md Step 5) — in most repos this is `#### 3b.` under `### 3.`.
**Leave everything after the gate list alone** — the "A block commits green…" paragraph, the box-ticking
step, and the commit block are unchanged by this release.

### M4 — `worker*.md`: run gates through make *(in-place, four edits — every worker file)*

Apply to **each** `worker*.md`; a per-stack worker names **its** stack's targets (`make web-build`,
`make gates-web`).

**M4a** — in `## Tools`, **above** the context-mode bullet:

> - **The `Makefile` — the only way you run a gate.** `make build`, `make test`, `make format`,
>   `make validate`, or `make gates` for the whole set in one `-k` pass. **Never call the underlying
>   toolchain directly** — the targets exist so every gate prints its exit code as `LABEL_EXIT:<n>` on its
>   last line, and that line is what you report. A gate passed only if you saw `BUILD_EXIT:0`; a tool can
>   exit non-zero while printing output that reads exactly like a clean run, so quote the code rather than
>   your reading of the log.

and in the context-mode bullet itself, replace the list of raw commands with "every `make` gate above"
and append: "Only the summary enters context — so make sure the `LABEL_EXIT:` line is in what you print."

**M4b** — in `## How you implement`, the **self-test** step: point it at `make build` / `make test` (or
`make gates`) and append:

> **Report the exit lines**, not a verdict: `BUILD_EXIT:0 TEST_EXIT:0` is a self-test result; "builds
> and tests pass" is a claim.

**M4c** — in `## Boundaries — what you must NOT do`, before the "The one thing you *do* write outside
code is the DEVLOG" bullet:

> - **Do not edit the `Makefile`, and do not route around it.** The gate targets are the Architect's. If
>   your block needs a target that doesn't exist (a new test project, a new stack) or an existing one
>   changed, **stop and report it** — don't add the target yourself, and don't fall back to running the
>   raw toolchain because `make` didn't cover you. A gate that ran outside the Makefile printed no exit
>   code, so nobody can check it.

**M4d** — in `## Stop and report`, after the "blocked by an unresolved Open Question" bullet:

> - the block needs a `Makefile` target that doesn't exist, or an existing target no longer covers what
>   it names (see Boundaries — the Makefile is the Architect's);

and in `## Communication`, replace "build/test status" with "the gate exit lines verbatim
(`BUILD_EXIT:0 TEST_EXIT:0`)".

### M5 — `reviewer.md`: verify gates by exit code *(in-place, two edits)*

**M5a** — in `## Tools`, above the context-mode bullet:

> - **The `Makefile`** — `make build`, `make test`, `make validate`, or `make gates` for the set.
>   **Never the raw toolchain.** Each target ends by printing `LABEL_EXIT:<n>`; that line is the
>   evidence, not the log above it. When you re-run a gate to check a worker's claim, cite the code you
>   saw — a tool can exit non-zero while printing what reads like a clean run.

and point the context-mode bullet at "the `make` gates" rather than the raw commands.

**M5b** — in `## What you check` → `### Correctness`, after the "Build is clean" bullet:

> - **The gates were actually run through the Makefile.** The worker's report should carry exit lines
>   (`BUILD_EXIT:0 TEST_EXIT:0`), not a prose claim that things pass. A block whose gates were run with
>   the raw toolchain, or reported as "green" with no exit code, is unverified — ask for the codes.
> - **The diff does not touch the `Makefile`.** Gate targets are the Architect's; a worker editing them
>   is a blocker, whatever the edit looks like.

### M6 — `supervisor.md`: read the exit lines, check gate coverage *(in-place, two edits)*

**M6a** — replace the **"You do not run the gates"** paragraph under `## Tools`:

> **You do not run the gates.** The Architect ran the Makefile's gates — `make build`, `make test`,
> `make validate` — on every block before committing it, and each printed its `LABEL_EXIT:<n>`. Read
> those exit lines in the DEVLOG rather than re-running anything; spend your budget on reading code. If a
> block's DEVLOG entry has no exit codes at all, that is a {{UNIT}}-level finding: a gate nobody can
> verify ran.

**M6b** — in `## What you check` → `### Cross-block coherence`, after the "Naming and layering" bullet:

> - **Gate coverage** — the `Makefile` still runs everything the {{UNIT}} shipped. A test project, a
>   package, or a whole stack added mid-{{UNIT}} that no gate target picks up is code that has never been
>   built or tested by the workflow, and no single block's diff shows it.

Substitute the repo's `{{UNIT}}` term in both.

### M7 — allowlist the gate targets *(new or merged `.claude/settings.json`, separate confirm)*

Offer to add exact-match permission rules for the targets M1 defined, to the **committed**
`.claude/settings.json` — not `settings.local.json`:

```json
{ "permissions": { "allow": [
  "Bash(make build)", "Bash(make test)", "Bash(make format)", "Bash(make lint)",
  "Bash(make validate)", "Bash(make gates)", "Bash(make changes)"
] } }
```

plus each additional stack's targets and gate set (`"Bash(make web-build)"`, `"Bash(make gates-web)"`,
`"Bash(make gates-all)"`). Omit any target the Makefile doesn't define.

**Ask separately** — accepting the Makefile is not consent to edit a permission config. Never
`"Bash(make *)"`; `publish` and `clean` are deliberately excluded so they keep prompting. **Merge** into
any existing `permissions.allow` array rather than replacing it — a pre-0.4.0 repo very likely has rules
there already, and losing them is a silent regression. Create the file with just this key if it's absent.

Mention that the agents run gates through context-mode (`ctx_execute`) for large output, which is a
separate MCP tool permission these Bash rules don't cover.

## In-flight changes

Mostly harmless mid-change: the gates are the same gates, invoked differently. Two things to say in the
SKILL.md Step 7 DEVLOG note:

- **blocks already landed have no exit codes in their DEVLOG entries.** That is expected and is not a
  finding — do not let the supervisor's new M6a clause fire retroactively on {{UNIT}}s built under
  0.3.x, and do not backfill exit codes into existing posts. The DEVLOG is append-only.
- from the next block on, gates run as `make <target>` and reports quote the exit line.

If the change is mid-{{UNIT}}, the remaining blocks of that {{UNIT}} will have mixed evidence in one
thread. That's fine and worth stating in the note so the supervisor reads it as a version boundary
rather than a lapse.

## Verify after applying

- `make gates` runs, and its output ends in `GATES_EXIT:<n>` — actually run it once.
- Recipe lines in the `Makefile` are **tab**-indented (`grep -P '^\t' Makefile` finds them).
- `make validate` fails, not passes, when there is no active change.
- No `#!!` line survives in the `Makefile`; the plain `#` header comments do.
- No raw toolchain command remains in `CLAUDE.md` or any agent — `grep -nE 'dotnet |npm |cargo |pytest'`
  over them should return nothing but prose.
- Every `worker*.md` (not just the first) got all four M4 edits, with its own stack's targets.
- `CLAUDE.md` §3b's gate list names targets and exit labels, and the paragraph after it is intact.
- `.claude/settings.json` is valid JSON (`jq -e . .claude/settings.json`) and its `permissions.allow`
  still contains every rule it had before M7.
- Every file the scaffold owns carries `<!-- dmons-scaffold: 0.4.0 -->` — and the `Makefile` carries
  `# dmons-scaffold: 0.4.0` on its first line.
