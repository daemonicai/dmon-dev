# Migration → 0.5.1 — the tripwire starts firing

**Applies to:** any repo scaffolded with **0.5.0** (stamped `<!-- dmons-scaffold: 0.5.0 -->`). A repo
coming from 0.4.x applies `0.5.0.md` first, then this note; from 0.3.x, `0.4.0.md` before those.

**This is a correctness fix, not a feature.** If the repo took M6 in 0.5.0, its tripwire has been
reporting "all clear" unconditionally since the day it was installed. Say that to the user plainly
before you start: they have not had detection, and the silence they were reading as verification was
the hook measuring an empty window.

## What was wrong

0.5.0 wired the tripwire as a `PreToolUse`/`PostToolUse` pair on `Agent|Task`. That assumed the Agent
tool call returns when the agent has finished. It doesn't — **subagents run in the background**, and the
tool call returns as soon as one is launched. So `post` fired a couple of seconds after `pre`, compared
two identical states, found nothing, and deleted the baseline. Everything the agent went on to do
happened after the comparison.

There was a second, independent break in the same script. `post` reported by returning
`{"decision":"block", …}` from a `PostToolUse` hook. Since Claude Code v2.1.210 that ends the turn and
prints the reason as a warning line in the chat — it does not feed it into the Architect's context. So
even a correctly timed comparison would not have delivered its report where the script's own comments
claimed it would.

Both are harness changes that landed under a script that was correct when it was written. The fix is to
stop inferring an agent's lifetime from a tool call and use the events that describe it directly.

## What 0.5.1 changes

`dmons-tripwire.sh` becomes a **three-mode script on three events**, replacing the two-mode script on
two:

| Mode | Event | What it does |
| --- | --- | --- |
| `start` | `SubagentStart` | Snapshots `HEAD` + tick counts as the agent spawns, keyed by `agent_id` |
| `stop` | `SubagentStop` | Recomputes both when *that agent* finishes; on drift, writes a report to disk |
| `report` | `Stop` | Runs at the end of the Architect's turn and hands over any reports waiting |

Three things this buys, each of which was a real defect before:

- **The window is the agent's actual lifetime.** `SubagentStop` fires when the subagent has finished
  responding, which is the moment the 0.5.0 pairing was reaching for and missing.
- **The correlation is exact.** `SubagentStart` and `SubagentStop` both carry `agent_id`, so concurrent
  agents cannot read each other's baselines. The old `tool_use_id` keying was fine in principle and
  moot in practice, since the comparison never happened.
- **The report reaches the Architect.** `stop` writes to disk and says nothing, because a `SubagentStop`
  hook talks to *the subagent* — a subagent's own `Stop` hook is converted to `SubagentStop` at runtime,
  so blocking there would feed the Architect's recovery instructions to the worker, which the guard has
  already blocked from git. Delivery happens on `Stop` in the Architect's session, where
  `decision: "block"` continues the Architect's turn with the reason as its next instruction.

Everything else about the workflow is untouched: same roster, same loops, same Makefile, same guard.

## Migrations, in order

### M1 — replace `dmons-tripwire.sh` *(in-place, full rewrite)*

Overwrite `.claude/hooks/dmons-tripwire.sh` from `scaffold/templates/dmons-tripwire.sh.template`,
stripped of its `#!!` lines and otherwise verbatim, then `chmod +x`. There is nothing to preserve from
the old one — no `{{PLACEHOLDER}}` slots, and no hand edits worth carrying across a rewrite this
complete. Confirm the execute bit with `test -x`.

`dmons-guard.sh` is **not** part of this migration. It blocks with `exit 2` from `PreToolUse`, which is
unaffected by the v2.1.210 change to JSON `decision` handling. Prevention has been working the whole
time; say so, because the natural reading of "the boundary hooks were broken" is that both halves were.

### M2 — rewire in `.claude/settings.json` *(in-place, replaces the 0.5.0 block)*

**Remove** the 0.5.0 `PreToolUse` and `PostToolUse` entries whose command contains
`dmons-tripwire.sh` — leave every other hook in those arrays alone, including the ones the repo had
before it was scaffolded. Then merge:

```json
{ "hooks": {
    "SubagentStart": [ { "matcher": "^(worker|worker-.+|reviewer|supervisor)$", "hooks": [ { "type": "command",
        "command": "\"$CLAUDE_PROJECT_DIR/.claude/hooks/dmons-tripwire.sh\" start" } ] } ],
    "SubagentStop":  [ { "matcher": "^(worker|worker-.+|reviewer|supervisor)$", "hooks": [ { "type": "command",
        "command": "\"$CLAUDE_PROJECT_DIR/.claude/hooks/dmons-tripwire.sh\" stop" } ] } ],
    "Stop":          [ { "hooks": [ { "type": "command",
        "command": "\"$CLAUDE_PROJECT_DIR/.claude/hooks/dmons-tripwire.sh\" report" } ] } ]
} }
```

Notes that matter when you merge:

- The `Stop` entry has **no matcher** — `Stop` doesn't take one. If the repo already has `Stop` hooks,
  append to the array.
- The matcher is a regex over the agent type, which for these project-level agents is the `name` from
  the agent file's frontmatter. If the repo's workers are named something other than `worker` or
  `worker-<stack>`, widen the alternation to match what `.claude/agents/` actually contains, and say
  which names you used. Getting this wrong is silent — the hook simply never fires.
- The script re-checks the agent type itself, so a merge that drops the matcher still behaves; the
  matcher is there to avoid running the hook at all for `Explore` and friends.

**Ask separately, as in 0.5.0.** This is still a `hooks` key running commands on your machine, and it is
still a legitimate thing to decline — but be straight about the asymmetry: declining in 0.5.0 meant
giving up detection, while declining here means *keeping a tripwire that reports all clear no matter
what happens*. If they decline, recommend removing the 0.5.0 entries anyway, so the repo has no
detection rather than fake detection.

`.gitignore` already has `.claude/.dmons-tripwire/` from 0.5.0; the new subdirectories (`open/`,
`pending/`, `delivered/`) live under it. If the entry is missing, add it.

### M3 — `CLAUDE.md`: correct the enforcement prose *(in-place, two edits)*

The 0.5.0 text describes a mechanism that no longer exists and, worse, tells the Architect to look for
the report at a moment when it cannot arrive.

Replace the tripwire bullet in **Boundaries — enforced by hooks, not by trust**:

> - **`.claude/hooks/dmons-tripwire.sh`** — it records `HEAD` and each active change's tick count when an
>   agent spawns, re-checks both when that agent finishes, and reports any movement to you at the end of
>   your turn. Agents run in the background, so this is deliberately not tied to the moment your `Agent`
>   call returns — that moment is the launch, not the finish.

And in §3b step 2, replace the "if the boundary tripwire fired on its return" sentence with:

> If the boundary tripwire reports at the end of your turn, deal with it **before** step 3 — an
> unreviewed, ungated commit is not a starting point for a review.

Leave the **When the tripwire fires** paragraph as it is; the recovery instructions were always right.

### M4 — re-verify enforcement end to end *(user action, not an edit)*

0.5.0 listed this as a bullet under "Verify after applying". Promote it to a step and actually run it,
because for the last release it was the **only** signal that enforcement was live, and the tripwire's
silence gave everyone the opposite impression.

1. Ask a worker to commit something. It should come back `BLOCKED by the OpenSpec Apply Workflow`.
2. If it commits instead, the frontmatter hooks are being skipped — the workspace was never trusted, or
   `dmons-guard.sh` lost its execute bit — and every agent has been running unguarded.

Two facts about trust worth passing on, because they make this fail silently in both directions:

- Frontmatter hooks in a project-level agent are skipped until the folder containing the agent file is
  trusted, and a `-p` session never counts as trusted.
- Before Claude Code v2.1.218 those hooks ran from untrusted folders too. So a repo that was demonstrably
  guarded before an upgrade can stop being guarded after one, with nothing in the transcript to say so.

Now that the tripwire works, step 1 has a second observable: the worker's commit attempt is blocked by
the guard *and*, if anything did slip past, the tripwire reports at the end of your turn.

## In-flight changes

Harmless mid-change. Nothing about how a block is built has changed — only whether the Architect finds
out when a boundary was crossed. As in 0.5.0: if an earlier {{UNIT}} contains a commit an agent made
itself, **leave it**. The DEVLOG is append-only and the history is what it is.

One thing worth a DEVLOG note this time, in the SKILL.md Step 7 slot: **any block completed under 0.5.0
was completed without detection.** The guard was preventing, so the likely answer is that nothing got
through — but "the tripwire stayed quiet" is not evidence for that period, and anyone reading the DEVLOG
later will assume it was.

  `dmons-tripwire.sh` command remains under `PreToolUse` or `PostToolUse`.

- The `SubagentStart`/`SubagentStop` matcher covers every worker name in `.claude/agents/` —

  `# dmons-scaffold: 0.5.1` on line 1 and each hook script on line 2.
- **The end-to-end check from M4 has actually been run**, not just read.
