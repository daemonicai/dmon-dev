# Migration → 0.3.0 — the section-level `supervisor`

**Applies to:** any repo scaffolded with **0.2.x or earlier** (i.e. no provenance stamp, and no
`.claude/agents/supervisor.md`).

## What changed in 0.3.0

The apply workflow gained a **second, outer loop**. Previously every block went worker → reviewer →
commit, and a section was just a container for blocks. Now each finished section gets a whole-section
audit from a new `supervisor` agent before the next section opens.

```
OUTER — for each ## N. {{UNIT}}, in order
  ├─ architect posts the {{UNIT}}'s base commit to the DEVLOG
  ├─ INNER — for each block (unchanged from 0.2.x)
  │    brief worker → worker implements → reviewer audits → gates → tick → commit
  └─ {{UNIT}} REVIEW — supervisor audits base..HEAD
       Approve → next {{UNIT}}
       Request changes → remediation block, re-enter INNER (max 2 rounds, then the Product Owner's call)
```

Alongside it, the **models moved**: `reviewer` dropped from opus to sonnet (it runs per block — the hot
path), and the new `supervisor` carries opus (it runs once per section). Net cost is roughly neutral;
the deep pass moved from per-block to per-section.

**Check the actual current value before assuming a downgrade.** Not every 0.2.x repo has an opus
reviewer — some were generated or hand-edited to sonnet already, in which case M2 is a no-op. Read the
frontmatter; don't infer it from the version.

**If M2 is a real downgrade (opus → sonnet), tell the user the trade-off first**, since it's the one
change with a behavioural cost: their per-block review gets weaker, and the supervisor is what backstops
it. Applying M2 while skipping M5 *downgrades the review with nothing replacing it* — refuse that
combination and say why. If the reviewer is already sonnet, the coupling doesn't apply and M5 stands on
its own merits.

## Harvest before applying

From the existing files (see SKILL.md Step 3), you need:

- the `{{UNIT}}` term in use — **critical**, see M9;
- project name + short description;
- binding decisions and the nouns used for them (`{{DECISIONS_NOUN}}`, `{{DECISIONS_NOUN_SINGULAR}}`,
  `{{DECISIONS_HEADING}}`, `{{COMPLIANCE_NOUN}}`);
- build/test commands, the `{{LANG}}` term;
- the reviewer's principal title (for M5's `{{SUPERVISOR_TITLE}}`, which must read a rung above it);
- whether the repo has ADRs (`{{ADR_CONTEXT_LINES}}`);
- **the reviewer's whole `## Tools` section, copied as-is** for `{{GRAPHIFY_TOOL_LINE}}` and its
  neighbours. Don't go looking for `graphify-out/` specifically — that slot's name is historical, and
  the repo may use different code-navigation tooling (CodeGraph, Serena, none). Whatever the reviewer
  lists is what the supervisor should list, minus the build/test lines it doesn't run (see M5).

**Audit fresh only for `{{ARCHITECTURAL_COHERENCE_BULLETS}}`** (M5). Nothing in the 0.2.x files
corresponds to it — it's the cross-block structural hazards, a different cut of the project from the
reviewer's per-block domain hazards. Derive it from `design.md` decisions, the specs, and the project
type. It **must not** restate the reviewer's `{{DOMAIN_HAZARDS}}`: if a check is answerable from one
block's diff, it belongs to the reviewer, not the supervisor.

## Migrations, in order

Apply in this order — M5 before the `CLAUDE.md` edits, so the workflow never references an agent that
doesn't exist yet.

### M1 — `reviewer.md`: add the diff-local fence *(in-place, additive paragraph)*

After the "you report findings; the worker fixes them" paragraph, insert:

> **Stay diff-local.** Once every block in a `## N.` {{UNIT}} has landed, a **`supervisor`** audits the
> {{UNIT}} as a whole — cross-block drift, duplicated abstractions, dead scaffolding, and whether the
> {{UNIT}} genuinely satisfies its spec. That is its job, not yours. Review the block in front of you
> thoroughly and let the {{UNIT}} take care of itself; if something in an *adjacent* block worries you,
> note it as an architectural note rather than expanding this review.

### M2 — `reviewer.md`: ensure `model: sonnet` *(in-place, one line — conditional)*

Frontmatter only. **Read the current value first:**

- `model: opus` → change to `sonnet`. This is a real downgrade; surface the trade-off, and **do not
  apply without M5** (see above).
- `model: sonnet` already → **no-op.** Report it as "already current", not as applied. Some 0.2.x repos
  were generated or tuned this way.

Every migration in this note is written to be **idempotent** — check the current state and skip cleanly
when it already matches, rather than assuming what the source version's template would have produced.
Files drift from their templates through hand edits, and a migration that assumes otherwise corrupts.

### M3 — `worker*.md`: remediation blocks *(in-place, additive paragraph — every worker file)*

In "Your job: implement one block", after the existing brief paragraph:

> Some blocks are **remediation blocks**: after all of a {{UNIT}}'s blocks land, a `supervisor` audits
> the {{UNIT}} as a whole and the Architect turns its findings into another block for you. These carry
> no new `N.M` task numbers — the brief cites the supervisor's DEVLOG post instead. Otherwise treat them
> exactly like any other block: implement the brief, hand off to `reviewer`, stay in scope. Fix what the
> findings name; don't take the occasion to tidy the rest of the {{UNIT}}.

### M4 — `worker*.md`: handoff boundary *(in-place, sentence — every worker file)*

Append to the "Do not self-approve" bullet:

> **Always to the reviewer, never `→ @supervisor`** — the Architect invokes the supervisor at {{UNIT}}
> end; it is not a handoff you make.

Also add the supervisor to the list of DEVLOG writers in that file's DEVLOG section.

### M5 — NEW `.claude/agents/supervisor.md` *(additive — new file)*

Fill `${CLAUDE_PLUGIN_ROOT}/skills/scaffold/templates/supervisor.md.template` from the harvest plus the
fresh `{{ARCHITECTURAL_COHERENCE_BULLETS}}` audit. Strip every guidance comment. Keep `model: opus`.

Its `## Tools` mirrors the reviewer's, **minus the build/test commands** — the supervisor reads gate
results from the DEVLOG rather than re-running them, so it needs the diff/log and navigation tools only.

Exactly one supervisor, even in a per-stack-worker repo.

### M6 — `CLAUDE.md`: roles *(in-place, additive)*

Add after the `reviewer` bullet:

> - **`supervisor`** agent — audits each finished `## N.` {{UNIT}} as a whole, once all its blocks have
>   landed (one supervisor for the whole change, every stack).

And after the roster, the paragraph distinguishing the two auditors ("The two auditors have different
jobs and must not be swapped…" — copy from `CLAUDE.md.template`).

### M7 — `CLAUDE.md`: restructure §3 *(in-place, structural — the big one)*

The largest edit. §3 becomes:

- an opening that states the two nested loops, with the ASCII diagram;
- **§3a — Opening a {{UNIT}}**: post the base commit (`**[architect]** Base: <sha> — …`);
- **§3b — Each block**: the existing numbered steps 1–7, **unchanged in substance**;
- **§3c — Closing a {{UNIT}}**: the supervisor review, remediation block, `fix(...)` commit, two-round
  cap.

Copy the structure from `CLAUDE.md.template` §3. **Preserve the repo's existing step 1–7 content
verbatim** — its gates, its commit block, its co-author line, any local additions. This migration
re-frames §3; it does not rewrite the block loop.

**Heading levels:** put 3a/3b/3c **one level below the repo's existing §3 heading**, not at the
template's absolute `###`. A generated `CLAUDE.md` normally sits one level deeper than the template, so
in most repos §3 is `### 3. Implement …` and the new sub-parts are `#### 3a.` / `#### 3b.` / `#### 3c.`.
Check before writing.

### M8 — `CLAUDE.md`: DEVLOG conventions *(in-place, additive)*

- Add the supervisor to the list of roles that write to the DEVLOG.
- Add the base-commit convention bullet:

  > **The first post under each `## N.` heading is the {{UNIT}}'s base commit** —
  > `**[architect]** Base: <sha> — <what this {{UNIT}} delivers>`. The supervisor's review scope is
  > `git diff <sha>..HEAD`, so this post is load-bearing, not ceremony.

### M9 — `{{UNIT}}` term consistency *(conditional — only if the term is NOT "section")*

**Skip this entirely if the repo's `{{UNIT}}` term is "section".**

0.2.x hardcoded the literal word "section" in `worker.md` and `reviewer.md` even when the repo's
`tasks.md` used a different container term (e.g. "group"). 0.3.0 uses the term consistently everywhere.
If this repo uses a different term, replace the literal "section" with it in both files wherever it
refers to a `## N.` container — **not** where it means "a section of this document".

### M10 — `CLAUDE.md`: §1 resume check *(in-place, additive)*

Add as §1.4:

> **Check the preceding {{UNIT}} closed.** Ticked boxes are not proof a {{UNIT}} passed its supervisor
> review — a session can end after the last block commits and before the review runs. Before starting
> the resume point's {{UNIT}}, read the DEVLOG: if the previous `## N.` has no `[supervisor]` `Approve`
> under it, run that review first (§3c). If it never got a `Base:` post either, reconstruct the range
> from `git log` and say so in the DEVLOG.

Without this, a session that dies between the last block's commit and the section review skips that
review permanently and silently.

### M11 — `CLAUDE.md`: §4 stop condition *(in-place, additive bullet)*

> - the **supervisor still requests changes after one remediation block** (§3c.4) — report its findings
>   and ask whether to remediate again, re-cut the {{UNIT}}, or fix the spec.

### M12 — `CLAUDE.md`: §5 Done *(in-place, one clause)*

The completion condition becomes "every task ticked **and the final {{UNIT}} has a supervisor
`Approve`**" — replacing "and the final review is clean". Add the supervisor's parked architectural
notes to what gets reported.

## In-flight changes

A change mid-apply has sections built under the old workflow — no base commits, no section reviews.
**Leave them.** The DEVLOG is append-only and is the durable record of how the change was actually
built. Post one `[architect]` note under the current heading saying the workflow changed and that
{{UNIT}} reviews start from the next {{UNIT}}, then let the Architect run 0.3.0 from there.

Do not carve a retroactive supervisor review for sections already closed under 0.2.x unless the user
explicitly asks — it is real work with a real cost, and it is their call, not the migration's.

## Verify after applying

- `.claude/agents/supervisor.md` exists, is `model: opus`, and contains no `{{PLACEHOLDER}}` or
  `<!-- -->` remnants.
- `reviewer.md` is `model: sonnet`.
- `CLAUDE.md` §3 has 3a / 3b / 3c, and §3b's gates and commit block are byte-identical to before.
- Every file the scaffold owns carries `<!-- dmons-scaffold: 0.3.0 -->`.
- The `{{UNIT}}` term is identical across `CLAUDE.md`, every worker, the reviewer, and the supervisor.
