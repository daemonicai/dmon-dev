# Migration → 0.5.0 — the boundaries become enforceable

**Applies to:** any repo scaffolded with **0.4.x** (stamped `<!-- dmons-scaffold: 0.4.0 -->`). A repo
coming from 0.3.x applies `0.4.0.md` first, then this note; from 0.2.x, `0.3.0.md` and `0.3.1.md` before
those.

## What changed in 0.5.0

The workflow shape is untouched — same two nested loops, same roster, same models, same Makefile. What
changed is that **three of its rules stopped being requests**.

Since 0.3.1 every agent's prompt has said the same three things: don't tick `tasks.md`, don't commit,
never invoke another agent. All three were prose, and prose is advisory. In practice a `worker` that has
just finished a block will sometimes tick its own tasks and commit its own work — and that is not a
tidiness problem: the Architect's gates, the reviewer's audit, and the tick that records them are the
only evidence a block was ever verified. Work that commits itself skips all three and looks identical
afterwards.

0.5.0 adds two hook scripts and the frontmatter that wires them:

- **`.claude/hooks/dmons-guard.sh`** — a `PreToolUse` hook wired from **each agent's own frontmatter**,
  so it sees that agent's tool calls and never the Architect's. It blocks git write subcommands, edits
  to `tasks.md` / `Makefile` / `CLAUDE.md` / `.claude/`, and any attempt to spawn an agent. It covers
  **both** Bash and the `ctx_*` context-mode tools, because those run commands too and the workflow
  deliberately routes its gates through them. The auditors (`reviewer`, `supervisor`) run it with the
  role `auditor`, which additionally confines their writes to `DEVLOG.md`.
- **`.claude/hooks/dmons-tripwire.sh`** — a `PreToolUse`/`PostToolUse` pair on the **Architect's** Agent
  calls, wired in `.claude/settings.json`. It records `HEAD` and each active change's tick count before
  an agent runs and re-checks after, then reports any movement into the Architect's context. Detection,
  not prevention: it catches what the guard couldn't see, and it still works in a repo where frontmatter
  hooks are being skipped.

Plus `disallowedTools: Agent, Task` on all three agent kinds, which removes the Agent tool outright
rather than asking them not to reach for it.

Both scripts are **verbatim copies** with no `{{PLACEHOLDER}}` slots. There is nothing to audit and
nothing to tailor.

## Harvest before applying

Almost nothing — this release adds files and frontmatter rather than rewriting audited prose. You need:

- the **worker roster** (`.claude/agents/worker*.md`), so every worker file gets M2, not just the first;
- the repo's `{{UNIT}}` term, for the CLAUDE.md prose in M4;
- whether `.claude/settings.json` exists and what it already contains.

Nothing needs a fresh audit.

## Migrations, in order

**M1 first** — the frontmatter in M2/M3 points at scripts that must exist. A missing script means a
failing hook, and a failing `PreToolUse` hook is **not** a denial: the agents would run unguarded and
look fine.

### M1 — write the two hook scripts *(new files)*

Copy `${CLAUDE_PLUGIN_ROOT}/skills/scaffold/templates/dmons-guard.sh.template` and
`dmons-tripwire.sh.template` to `.claude/hooks/dmons-guard.sh` and `.claude/hooks/dmons-tripwire.sh`.
Strip every `#!!` line; **keep** the plain `#` comments. Stamp each on the **second** line, directly
below the shebang: `# dmons-scaffold: 0.5.0`.

Then **`chmod +x` both and verify it** (`test -x`). This is the step that silently breaks the whole
migration if skipped.

Do not edit either script. They hold no repo-specific values, so anything you "adapt" is a hole.

### M2 — every `worker*.md`: frontmatter *(in-place, additive)*

Add to the frontmatter of **each** worker file — one per stack in a per-stack repo:

```yaml
disallowedTools: Agent, Task
hooks:
  PreToolUse:
    - matcher: "Bash|PowerShell|Edit|Write|MultiEdit|NotebookEdit|Agent|Task|.*ctx_execute.*|.*ctx_batch_execute.*"
      hooks:
        - type: command
          command: '"$CLAUDE_PROJECT_DIR/.claude/hooks/dmons-guard.sh" worker'
```

Leave `name`, `description`, and `model` exactly as they are.

### M3 — `reviewer.md` and `supervisor.md`: frontmatter *(in-place, additive)*

The same block, with the role **`auditor`** instead of `worker`:

```yaml
disallowedTools: Agent, Task
hooks:
  PreToolUse:
    - matcher: "Bash|PowerShell|Edit|Write|MultiEdit|NotebookEdit|Agent|Task|.*ctx_execute.*|.*ctx_batch_execute.*"
      hooks:
        - type: command
          command: '"$CLAUDE_PROJECT_DIR/.claude/hooks/dmons-guard.sh" auditor'
```

**Get the role right.** An auditor wired as `worker` can edit the whole tree — exactly the review the
workflow was built to prevent — and nothing in the transcript would show it.

### M4 — the agents' Boundaries sections *(in-place, additive paragraph)*

Each agent's `## Boundaries` section now opens with a paragraph saying the rules are enforced and what a
block looks like, so an agent that hits one recognises it as designed behaviour rather than a broken
tool and stops instead of hunting for another route.

For every `worker*.md`, insert directly under the `## Boundaries — what you must NOT do` heading:

> **These are enforced, not requested.** A `PreToolUse` guard on this agent blocks the tool calls below
> before they run, whichever tool you reach for — Bash, an editor, or a `ctx_*` command. A block reads
> `BLOCKED by the OpenSpec Apply Workflow` and names the boundary. When you see one, **stop**: it is not
> a permission prompt, not a flaky tool, and not something to work around by another route. Post the
> reason to the DEVLOG and hand back to the Architect. That hand-back is the designed outcome, not a
> failure.

and add one bullet to that list:

> - **Do not edit `CLAUDE.md` or anything under `.claude/`.** That is the workflow you are running
>   inside — the agent definitions, the guard, the permission config. Changing it from within a block
>   changes the rules you are being held to.

For `reviewer.md` and `supervisor.md`, insert under their `## Boundaries` heading:

> **These are enforced, not requested.** A `PreToolUse` guard on this agent blocks the calls below
> before they run — `DEVLOG.md` is the only file you can write, and git's history is closed to you. A
> block reads `BLOCKED by the OpenSpec Apply Workflow`. When you see one, stop and post the finding
> instead; that is what the guard is steering you back to.

Leave the existing bullets alone.

### M5 — `CLAUDE.md`: the enforcement section *(in-place, new subsection)*

After the `### Commands — the Makefile is the command surface` section (immediately after its closing
"**The Makefile is yours (Architect), not the workers'**" paragraph), add a sibling subsection at the
**same heading level**:

> ### Boundaries — enforced by hooks, not by trust
>
> Three things belong to you alone: **the commits, the ticked boxes, and the decision to invoke an
> agent.** Those rules are written into every agent's prompt, and they are also enforced, because a rule
> that only exists as prose is one an agent under pressure to finish a block will eventually break.
>
> - **`.claude/hooks/dmons-guard.sh`** — a `PreToolUse` hook wired into each agent's own frontmatter, so
>   it sees that agent's tool calls and never yours. It blocks git writes, edits to `tasks.md`, the
>   `Makefile`, `CLAUDE.md` and `.claude/`, and any attempt to spawn another agent — across Bash *and*
>   the `ctx_*` tools, since those run commands too. The auditors (`reviewer`, `supervisor`) are further
>   confined to writing `DEVLOG.md` and nothing else.
> - **`.claude/hooks/dmons-tripwire.sh`** — a `PreToolUse`/`PostToolUse` pair on **your** Agent calls. It
>   records `HEAD` and each active change's tick count before an agent starts and re-checks after it
>   returns, so anything the guard didn't catch still surfaces — in your context, immediately, instead of
>   in a commit log nobody reads.
>
> **When the tripwire fires, it is telling you the block skipped a gate.** Don't accept the state and
> move on: read what landed, then `git reset --soft <the sha it names>` to put the work back in the tree
> without the agent's commit, untick anything you didn't tick, and run the block through the rest of the
> loop — reviewer, gates, your tick, your commit. Record it in the DEVLOG. The work is often fine; the
> problem is that nothing verified it, and that's exactly what the loop exists to do.
>
> Neither hook constrains you. You commit, you tick, you spawn the agents.

Drop the tripwire bullet if M6 is declined, and say so in the report.

Also extend §3b step 2 (**Worker implements the block**) with:

> If the boundary tripwire fired on its return, deal with that **before** step 3 — an unreviewed,
> ungated commit is not a starting point for a review.

and append to the §3 paragraph that begins "**You are the only agent that invokes agents.**":

> The agents have no Agent tool at all, so this is a fact about them rather than an instruction to them.

### M6 — wire the tripwire in `.claude/settings.json` *(separate confirm)*

Merge into the **committed** `.claude/settings.json` — not `settings.local.json`:

```json
{ "hooks": {
    "PreToolUse":  [ { "matcher": "Agent|Task", "hooks": [ { "type": "command",
        "command": "\"$CLAUDE_PROJECT_DIR/.claude/hooks/dmons-tripwire.sh\" pre"  } ] } ],
    "PostToolUse": [ { "matcher": "Agent|Task", "hooks": [ { "type": "command",
        "command": "\"$CLAUDE_PROJECT_DIR/.claude/hooks/dmons-tripwire.sh\" post" } ] } ]
} }
```

**Ask separately.** A `hooks` key runs commands on every matching tool call — a larger consent than the
0.4.0 permission rules, and one someone can reasonably decline. Read the file first and merge: an
already-scaffolded repo has a `permissions.allow` array a wholesale write would drop, and it may already
have `hooks` entries of its own, which you append to rather than replace.

Add `.claude/.dmons-tripwire/` to `.gitignore`.

**Declining M6 is a legitimate outcome** and does not block M1–M5: the guard still prevents, there is
just no detection behind it. Say which half they have.

### M7 — trust the workspace *(user action, not an edit)*

Project-level agent frontmatter hooks are skipped until the folder containing the agent files is
trusted, and Claude Code skips them **quietly** — the agent still runs, unguarded, and nothing in the
transcript says otherwise. Tell the user to accept the workspace trust prompt for this repo, and give
them the verification below.

## In-flight changes

Harmless mid-change: nothing about how a block is built has changed, only what the agents are physically
able to do. One thing for the SKILL.md Step 7 DEVLOG note:

- if an earlier {{UNIT}} in this change contains a commit an agent made itself, **leave it**. The DEVLOG
  is append-only and the history is what it is; note that the boundary is now enforced from here on
  rather than rewriting the record to look like it always was.

## Verify after applying

- `test -x .claude/hooks/dmons-guard.sh && test -x .claude/hooks/dmons-tripwire.sh` — both executable.
- `jq -e . .claude/settings.json` parses, and `permissions.allow` still holds every rule it had before.
- `command -v jq` — the guard fails closed without it, so a machine with no `jq` blocks every agent
  tool call.
- No `#!!` line survives in either script; the plain `#` comments do.
- Every `worker*.md` (not just the first) has the `worker` role in its hook command; `reviewer.md` and
  `supervisor.md` have `auditor`. `grep -n 'dmons-guard' .claude/agents/*.md` shows one line each, with
  the right role.
- **The end-to-end check, worth doing once:** ask a worker to commit something. It should come back with
  `BLOCKED by the OpenSpec Apply Workflow`, not a commit. A worker that commits means the frontmatter
  hooks are being skipped — untrusted workspace (M7) or a missing execute bit (M1) — and every agent is
  running unguarded.
- Every file the scaffold owns carries `<!-- dmons-scaffold: 0.5.0 -->`; the `Makefile` carries
  `# dmons-scaffold: 0.5.0` on line 1 and each hook script on line 2.
